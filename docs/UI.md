# Web-интерфейс LMS

> Актуально после **этапа 2**. Интерфейс использует только те API, которые уже
> реализованы (auth, course, enrollment, notification через gateway), и не
> обещает функциональности следующих этапов.

## 1. Что это

Одностраничное приложение на нативных ES-модулях без сборки и без npm-зависимостей.
Всё, что нужно браузеру, — `index.html`, `css/app.css` и каталог `js/`.

| Экран | Маршрут | Доступ | Что делает |
| :--- | :--- | :--- | :--- |
| Вход | `#/login` | гость | логин, демо-подсказка, настройки API |
| Регистрация | `#/register` | гость | создаёт аккаунт (`STUDENT`) и сразу входит |
| Каталог | `#/catalog` | JWT | список курсов, поиск, фильтр по публикации, создание курса |
| Курс | `#/courses/:id` | JWT | модули и уроки, управление для владельца/ADMIN, запись и прогресс для студента |
| Мои курсы | `#/my-courses` | JWT | записи студента, прогресс по урокам, отмена записи |
| Уведомления | `#/notifications` | JWT | свои события; колокольчик в шапке показывает счётчик «новых» |
| Профиль | `#/profile` | JWT | кто вошёл, TTL токена, роли, админ-панель, настройки API |
| 404 | любой другой | — | объяснение и ссылки назад |

Ролевое поведение повторяет бэкенд (источник правды — сервисы):

| Действие | STUDENT | INSTRUCTOR | ADMIN |
| :--- | :---: | :---: | :---: |
| Смотреть каталог и курс | да | да | да |
| Создать курс | — | да | да |
| Править/удалять курс | — | только свой | любой |
| Публикация, модули, уроки | — | только свой курс | любой курс |
| Записаться / отменить запись | да | — | — |
| Отметить урок пройденным | своя запись | — | — |
| Менять роли | — | — | да |

«Мои курсы» появляется в навигации только при роли STUDENT; уведомления
видят все аутентифицированные пользователи (колокольчик в шапке).

## 2. Как запустить

### Основной путь (как в README)

```bash
cd infra
docker compose up -d --build      # postgres, rabbitmq, auth, course, gateway, web
# UI: http://localhost:8088
```

`web` — контейнер nginx (`infra/Dockerfile.web`). Он отдаёт статику и
проксирует `/api` на `gateway-service:8080`, поэтому браузер видит один origin:

```
браузер → http://localhost:8088
            ├── /            → index.html + css/js (nginx)
            ├── /api/...     → gateway-service:8080 → auth / course
            └── /healthz     → gateway /actuator/health
```

Проверка без браузера (36 проверок: статика, прокси, логин, 401, ротация,
enrollment/notifications через gateway, новые модули статики):

```bash
powershell -File scripts/smoke-web.ps1     # Windows PowerShell 5.1+ / pwsh
bash scripts/smoke-web.sh                  # Git Bash / WSL / Linux
```

### Режим разработки (без пересборки образа)

```bash
cd web
node scripts/dev-server.js                 # http://localhost:5500
```

Сервер отдаёт `web/` и проксирует `/api` и `/healthz` на `http://localhost:8080`
(переопределяется `API_TARGET`). Изменения в css/js видны после F5, Docker не нужен.

Альтернатива — открыть `web/` любым статическим сервером и указать абсолютный
адрес API: `http://localhost:5500/?api=http://localhost:8080/api` (или через
«Настройки API» в подвале). Этот путь использует CORS gateway — origin должен
быть в `LMS_CORS_ALLOWED_ORIGINS` (по умолчанию 8088 и 5500 разрешены).

### Тесты

```bash
cd web
node test/run.js                           # 78 unit-тестов, без зависимостей и без spawn
node test/ui-e2e.mjs --base-url http://localhost:8088   # 62 проверки в реальном Chrome
```

`ui-e2e.mjs` управляет headless Chrome по DevTools Protocol (без Playwright):
логин → создание курса → модуль → урок → правка → публикация → выход, затем
регистрация студента: запись на курс (с ретраями, пока снапшот курса не долетел
до enrollment-service), отметка урока, экраны «Мои курсы» и «Уведомления», и
в конце администратор удаляет курс. Сценарий создаёт временный курс (удаляет
за собой) и **регистрирует тестового студента** — на локальной базе это
нормально, на общей лучше не запускать.

`test/browser-smoke.html` — ручная проверка API из браузера без UI
(`?auto=1&email=…&password=…&write=1`), полезна при отладке CORS/прокси.
В образ nginx она не попадает (копируются только `index.html`, `css`, `js`).

## 3. Структура `web/`

```
web/
├── index.html                 # каркас: шапка, #view, подвал, #toasts, noscript
├── nginx.conf                 # статика + /api + /healthz
├── package.json               # только скрипты; зависимостей нет
├── css/app.css                # токены тем + компоненты (один файл)
├── js/
│   ├── main.js                # сборка приложения, истечение сессии, ping, опрос уведомлений, настройки
│   ├── core/                  # без бизнес-логики и без привязки к DOM
│   │   ├── config.js          # адрес API: ?api= → localStorage → __LMS_CONFIG__ → /api
│   │   ├── jwt.js             # декодирование claims (подпись проверяет бэкенд)
│   │   ├── session.js         # пара токенов, профиль, роли, canManageCourse
│   │   ├── http.js            # fetch + таймаут + разбор problem+json
│   │   ├── errors.js          # ApiError, describeError, fieldErrorsOf
│   │   ├── client.js          # Bearer, проактивный refresh, single-flight, 401-retry
│   │   ├── router.js          # hash-роутер, guard-ы, loading/error состояния
│   │   ├── format.js          # даты, «5 минут назад», склонения, инициалы
│   │   ├── enrollment.js      # прогресс/поиск записей поверх ответов enrollment-service
│   │   └── notifications.js   # клиентский счётчик «новых» уведомлений (localStorage)
│   ├── api/
│   │   ├── auth.js            # register/login/refresh/logout/me/changeRole
│   │   ├── courses.js         # курсы, модули, уроки, публикация
│   │   ├── enrollments.js     # запись, отмена, прогресс уроков (этап 2)
│   │   └── notifications.js   # список своих уведомлений (этап 2)
│   ├── ui/
│   │   ├── dom.js             # el()/frag()/text(), запрет innerHTML
│   │   ├── icons.js           # инлайновые SVG-иконки
│   │   ├── layout.js          # шапка (навигация по ролям, колокольчик), подвал, статус API
│   │   ├── forms.js           # декларативные поля + клиентская валидация
│   │   ├── modal.js           # <dialog>: форма, подтверждение
│   │   ├── states.js          # загрузка, пусто, ошибка, скелетоны
│   │   ├── toast.js           # уведомления (aria-live)
│   │   ├── theme.js           # светлая/тёмная тема
│   │   └── api-settings.js    # диалог «Настройки API» с проверкой соединения
│   └── views/                 # экраны; контракт: (ctx) → { el, title?, dispose? }
│       ├── auth-shell.js      # общая оболочка входа/регистрации
│       ├── login.js, register.js, catalog.js, course.js, profile.js, not-found.js
│       ├── my-courses.js      # записи студента и прогресс (этап 2)
│       └── notifications.js   # список уведомлений, отметка просмотра (этап 2)
├── scripts/dev-server.js      # статика + прокси для разработки
└── test/                      # unit-тесты, browser-smoke, ui-e2e
```

Правила, которые действуют внутри `web/`:

1. **`core/` не знает про DOM и UI.** Поэтому его можно тестировать в Node.
2. **`api/` — только методы сервисов.** Никакой вёрстки и никаких токенов.
3. **`ui/` — переиспользуемые кирпичи.** Никаких знаний про конкретные эндпоинты.
4. **`views/` — сценарии экрана.** Возвращают DOM (или `{ el, title, dispose }`).
5. **Пользовательский текст — только через `textContent`** (`el()` бросает
   исключение на проп `html`).

## 4. Сессия и токены на клиенте

* Хранение: `localStorage['lms.session.v1']` = `{ accessToken, refreshToken, savedAt, user }`;
  `expiresAt` и роли выводятся из JWT при чтении.
* Access-токен живёт 15 минут. Перед запросом клиент проверяет `exp` и, если до
  истечения меньше 30 секунд, обновляет пару заранее — без лишнего 401.
* При 401 клиент один раз обновляет пару и повторяет исходный запрос.
* **Refresh single-flight:** параллельные запросы не отправляют несколько
  refresh подряд. Это критично: auth-service считает повторное предъявление
  отозванного refresh-токена атакой и гасит все сессии пользователя.
* **Синхронизация вкладок:** Web Locks (`navigator.locks`) плюс сравнение
  актуального токена в `localStorage`; событие `storage` обновляет шапку, а
  выход в одной вкладке разлогинивает остальные.
* Если refresh не удался — сессия очищается, пользователь видит предупреждение
  и попадает на `#/login?next=<куда шёл>`.
* Выход дополнительно вызывает `POST /api/auth/logout` и отзывает refresh-токен.

Роль берётся из `user.role` (`/api/auth/me`) и `roles` из JWT. Если после смены
роли администратором токен содержит старую роль, профиль показывает
предупреждение и предлагает перелогиниться.

## 5. Запись на курс, прогресс и уведомления (этап 2)

### Запись на курс

* На странице опубликованного курса студент видит панель «Запись на курс»
  с кнопкой «Записаться»; подпись показывает актуальный `enrolledCount`.
* Бэкенд отвечает 404 «Course is not available yet», пока событие
  `course.published` ещё не долетело до снапшота enrollment-service. UI в
  этом случае показывает тост с подсказкой «подождите пару секунд» — это
  ожидаемый race, а не ошибка пользователя.
* У активной записи панель превращается в «Прогресс обучения»: полоса
  прогресса, «Пройдено N из M уроков» и кнопка «Отменить запись» (с
  подтверждением). Отмена не удаляет прогресс, но отмечать уроки можно
  только при активной записи.
* Записаться может только STUDENT (та же проверка, что и на бэкенде).

### Прогресс уроков

* У каждого урока при активной записи есть кнопка «Отметить пройденным»
  (идемпотентный `POST /lessons/{id}/complete`); пройденный урок получает
  класс `.lesson--done` и подпись «Пройден».
* Процент считается на клиенте: пройденные `lessonId` из записи против
  списка уроков курса (course-service). Логика — в `core/enrollment.js`.
* Экран `#/my-courses` показывает активные записи и архив со статусами
  ACTIVE / COMPLETED / CANCELLED.

### Уведомления

* Список — `GET /api/notifications` (до 100, свежие первыми) на экране
  `#/notifications`; имена типов (USER_REGISTERED, ENROLLMENT_CREATED,
  LESSON_COMPLETED) подменяются на понятные иконки и текст из бэкенда.
* Отметки «прочитано» на этапе 2 нет, поэтому «новые» считаются на клиенте:
  всё, что пришло позже последнего открытия экрана. Момент просмотра —
  `localStorage['lms.notifications.seenAt']`, логика — в `core/notifications.js`.
* Опрос раз в 60 секунд (вместе с ping API) и при смене сессии; открытие
  экрана уведомлений снимает счётчик. Сбой опроса не мешает работе UI.

## 6. Ошибки

Бэкенд отвечает RFC 9457 (`application/problem+json`). Клиент приводит любой
ответ к `ApiError`:

| Ситуация | Что видит пользователь |
| :--- | :--- |
| 400 + `errors` | сообщение под каждым полем формы + общий алерт |
| 401 | «Требуется вход» + переход на логин |
| 403 | «Недостаточно прав: …» (действие владельца/ADMIN) |
| 404 | «Ресурс не найден» + «Повторить» |
| 409 | конфликт (например, email уже занят) |
| 5xx | «Ошибка сервера (N)» |
| сеть/таймаут | «Сервер недоступен» + подсказка про `docker compose` и настройки API |

Технические детали ошибки дублируются в консоль браузера, но не в интерфейс.

## 7. Безопасность на клиенте

* Подпись JWT клиент **не проверяет** и не может: claims читаются только для UX
  (роли, время жизни). Авторизация — на gateway и в сервисах.
* Нет `innerHTML`: имена курсов, описания и содержимое уроков вставляются
  текстовыми узлами — XSS через данные API невозможен.
* Refresh-токен лежит в `localStorage`. Для локального pet-проекта это осознанный
  компромисс; в проде нужен `httpOnly`-cookie + CSRF-защита на бэкенде.
* CORS на gateway разрешает только перечисленные origin (не `*`), потому что
  токен хранится на клиенте.
* CSP пока не настроена (в `index.html` есть инлайновый diagnostic-script);
  при переходе на этап 7 её стоит добавить вместе с HTTPS-only.

## 8. Ограничения этапов 1–2

Чего в интерфейсе **нет** и почему:

* **Оценивание** — появится на этапе 3 (`assessment-service`). Запись и
  прогресс уроков уже работают, к ним добавится результат теста/задания.
* **Список пользователей** — в auth-service есть только
  `PATCH /users/{id}/role`, поэтому админ вводит `userId` вручную; в панели
  есть быстрые подсказки из `instructorId` курсов.
* **Видимость черновиков** — `GET /api/courses` отдаёт черновики любому
  аутентифицированному пользователю (ограничение бэкенда этапа 1). UI по
  умолчанию показывает опубликованные курсы студенту и все — инструктору.
* **Пагинация и серверный поиск** — списковых параметров у API нет; поиск и
  счётчики считаются на клиенте по загруженному списку.
* **Отметка «прочитано» у уведомлений** — PATCH-эндпоинта на этапе 2 нет;
  счётчик «новых» живёт в localStorage конкретного браузера и не переносится
  между устройствами.
* **Прогресс цитирует только уроки** — score (`score` в `lesson_progress`)
  сбережён для этапа 3.
* **Загрузка файлов** — этап 4 (media-service).
* **Интернационализация** — интерфейс русскоязычный, как и документация.

## 9. Что дальше

При появлении новых сервисов интерфейс расширяется без переписывания ядра:

1. `assessment-service` (этап 3) → прохождение теста и результат в уроке,
   оценки в прогрессе enrollment.
2. `media-service` (этап 4) → вложение `mediaId` к уроку и плеер по presigned URL.
3. `PATCH /api/notifications/{id}/read` → «прочитано» на бэкенде, когда появится.
4. Списки пользователей / инструкторский вид записавшихся → если войдёт в объём.

Добавление экрана — это новый файл в `views/`, маршрут в `main.js`, метод в
`api/`. Ядро (`core/`) при этом не меняется.
